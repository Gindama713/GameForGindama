## 三、🔴 严重（会造成静默失效或改一处漏一处）

### S1 · 需求 id 常量**同值复制**（4 个文件声明同一个字符串）

**范围**：`creature/components/` 下 6 个组件

| 字面量 | 声明处 | 处数 |
|---|---|---|
| `"fatigue"` | `brain.gd:44` `FATIGUE_ID` · `needs.gd:13` `FATIGUE_ID` · `sleep.gd:355` `FATIGUE_ID` · `sprint.gd:66` `STAMINA_ID` | **4** |
| `"water"` | `drinking.gd:26` `THIRST_ID` · `grazing.gd:37` `WATER_ID` · `reproduction.gd:14` `WATER_ID` | **3** |
| `"food"` | `grazing.gd:36` `FOOD_ID` · `reproduction.gd:13` `FOOD_ID` | **2** |

**为什么严重** —— 它是**双向静默失效**：

1. `.tres` 里把 `id = "fatigue"` 改成别的 → 必须同时改这 4 处常量；漏一处 → `need_by_id()` 返回 `null`；
2. 而**每个调用点都写了 `if n == null: return` 的兜底**（这是好习惯）——
   于是结果是：**不报错、不崩溃，只是那个机制悄悄不工作了**。
   例：只改了 `sprint.gd` 的 `STAMINA_ID` → **疾跑永远不消耗体力**，而且没有任何日志。

**这正是项目自己批判过的病**。`common/groups.gd` 的注释原话：

> 这些字符串此前**散在三处各写一遍**，而且每处的注释都写着"与 XXX 同一个字面量" ——
> 那正是"同值复制"的自我供认：改一处忘一处，而且没人知道还有谁在用这个数（隐式耦合）。

而 `brain.gd:44` 的注释也写着「**别再散写字符串**」—— 但那条纪律**只约束了"不要写裸字符串"，没管"常量本身也重复了"**。

**建议（保持功能不变）**：照 `common/groups.gd` 的成熟做法，把需求 id 收到**一个中立常量类**：

```gdscript
# creature/need_ids.gd（新建，与 common/groups.gd 同款）
class_name NeedIds
extends RefCounted

## 需求 id 的**唯一事实来源**。⚠ 加新需求只在这里加。
## 【为什么需要它】此前 "fatigue" 在 4 个组件里各声明一次、"water" 3 次、"food" 2 次 ——
##   同值复制。改一处忘一处 ⇒ `need_by_id()` 返回 null ⇒ 各组件都有 `if n == null: return`
##   的兜底 ⇒ **不报错、只是那个机制悄悄不工作了**。
const FATIGUE := "fatigue"
const FOOD := "food"
const WATER := "water"
const WARMTH := "warmth"
```

然后各组件改 `const FATIGUE_ID := NeedIds.FATIGUE`（保留本地别名，调用点一行不用动）。
**收益**：改 id 只需改 1 处；**并且可以顺手加一条校验**（见下）。

**额外加固（可选，但很值）**：给 `Needs` 加一条启动期自检 ——
「物种 def 里声明的 need id 集合」必须覆盖「所有组件引用到的 need id」。
这样漏改就从"静默"变成"启动就报错"。

### S2 · `player_def.tres` 引用 **`creature/pig/...`**（跨物种数据依赖）

**范围**：`creature/player/player_def.tres` 的 6 条 `ext_resource`

```
res://creature/pig/pig_life.tres          ← 寿命
res://creature/pig/pig_temperament.tres   ← 脾气
res://creature/pig/data/need_food.tres    ← 饥饿
res://creature/pig/data/need_water.tres   ← 口渴
res://creature/pig/data/need_warmth.tres  ← 保暖
res://creature/pig/data/need_fatigue.tres ← 疲劳
```

**为什么严重** —— 违反项目自己写下的规则：

> **目录位置即复用范围的声明**（`creature/<物种>/` = 只有这一个物种需要）

主角**不是猪**，却读猪的数据目录。三个后果：

1. **改猪的寿命/需求 → 主角跟着变**，而且是**隐式的**（没有任何注释或类型系统提示这两个物种耦合）；
2. **删 / 重命名 / 重构 `creature/pig/` → 主角直接断**（加载失败）；
3. 加第三个物种时，"哪些数据是共享的、哪些是物种专属"**没有地方表达** —— 只能继续复制或继续跨引用。

**注意**：`player_def.tres` 的注释里**明确承认了这件事**（"需求数据仍复用猪的 `pig/data/need_*.tres`；人猪需求同值，先不复制一份"）——
所以这是**有意识的取舍**，不是疏忽。但它的代价是隐式耦合，而且随着物种变多会恶化。

**建议（保持功能不变）**：把**共享**的那部分提出来，让两个物种都引用它，而**不是**让一个物种引用另一个：

```
creature/
├─ shared/                     ← 新建：跨物种共享的数据
│  ├─ life_common.tres         ← 从 pig_life.tres 提出来
│  ├─ temperament_common.tres  ← 从 pig_temperament.tres 提出来
│  └─ need_{food,water,warmth,fatigue}.tres
├─ pig/     → 引用 creature/shared/...
└─ player/  → 引用 creature/shared/...
```

⚠ **一个必须同步改的地方**：`common/def_validator.gd` 的 `SCAN_ROOTS` 只扫
`res://creature`（含子目录）—— 新建 `creature/shared/` **会被自动覆盖** ✓，不用改。
但如果你把共享数据放到 `creature/` **之外**，就**必须**同步加进 `SCAN_ROOTS`，否则
"0 条问题"和"根本没扫到"就长得一样了（§6.10.2）。

**收益**：物种之间**不再互相引用**；"共享 vs 专属"在目录上一眼可见。

### S3 · `ui/player_panel.gd` 硬编码**主角的部位版式与立绘路径**

**范围**：`ui/player_panel.gd:65–133`

```gdscript
const PART_LAYOUT := { ... }          # 部位 → 面板坐标
const PART_TEXTURE := {               # 部位 → 立绘路径（7 条 res://）
    "head": "res://creature/player/art/brain.png",
    "ribcage": "res://creature/player/art/ribcage.png",
    "arm_l": "res://creature/player/art/arm.png",
    "arm_r": "res://creature/player/art/arm.png",
    "leg_l": "res://creature/player/art/leg.png",
    "leg_r": "res://creature/player/art/leg.png",
}
const PART_FLIP := {}                 # 部位 → 是否水平翻转
const PORTRAIT_TEX := preload("res://creature/player/art/person.png")
```

**为什么严重（可复用性）** —— 这些是**数据**（部位 → 素材 / 坐标 / 翻转），却写死在 **UI 脚本**里：

1. 换一张立绘 → 要改 **UI 代码**（而不是换素材或改 `.tres`）；
2. 加一个部位 / 加一个物种 → 要改 **UI 代码**；
3. 而 `BodyPartDef` 已经有 `id` / `label` / `max_hp` / `limb_types` / `category` ——
   **加一个 `texture` 与 `panel_pos` 字段就能完全数据化**，UI 只按 `id` 查表；
4. 更糟的是：**同样的信息在 `creature/player/data/part_*.tres` 里已经存在一份**（`id`/`label`），
   于是"部位清单"在数据与 UI 代码里各有一份 —— **又一处同值复制**。

**建议（保持功能不变，分两步走）**：

- **第一步（低风险，推荐先做）**：把 `PART_LAYOUT`/`PART_TEXTURE`/`PART_FLIP`/`PORTRAIT_TEX`
  抽到一个**数据文件** `creature/player/panel_layout.tres`（一个自定义 `Resource`，
  字段是 `Dictionary` 或 `Array[PanelPartDef]`），`player_panel.gd` 只读它。
  **UI 里不再出现任何 `res://`**。
- **第二步（更彻底）**：把 `texture` / `panel_pos` 直接放进 `BodyPartDef`，
  UI 完全不需要映射表 —— 但这一步会改 `BodyPartDef` 的结构，建议单独一轮。

**同时建议**：`ui/family_tree.gd:13` 也硬编码了 `PIG_TEX := preload("res://creature/pig/art/pig.png")`，
它是"家谱里没有立绘时的兜底图标"——**在一个通用 UI 里写死了猪**。

> 这个项目**自己已经知道**了：`family_tree.gd:121` 的注释写着
> 「`_draw()` 一律画 PIG_TEX → 主角（人）在族谱里"还是一头猪"」。
> 所以它是**已知限制**，不是疏忽 —— 但既然要列"可复用性问题"，它就该在清单上。
> 修法同上（兜底图标进数据，或改用 `def.texture`）。

## 四、🟠 中等（会造成**静默退化**或隐性契约）

### M1 · `Log.ev` 的分类名在 **25 处**硬写中文

**范围**：`common/log.gd` 的 `categories` 字典（8 个分类）vs 25 个调用点

| 分类 | 调用处数 |
|---|---|
| `"睡眠"` | 6 |
| `"生成"` | 5 |
| `"受伤"` `"需求"` `"疾跑"` `"调试"` | 各 2 |
| `"死亡"` `"移动"` | 各 1 |

**为什么是问题** —— `log.gd` 的字典是**唯一事实来源**，但调用点各自硬写中文：

```gdscript
func ev(category: String, msg: String) -> void:
	if not enabled or not categories.get(category, true):   # ← 未知分类默认「开」
		return
```

`categories.get(category, true)` 的默认值是 `true`，所以拼错分类名的后果是：
**静默多出一个"默认开"的分类，而且用原名 `Log.set_category("睡眠", false)` 关不掉它**
（因为实际记录的 key 是错别字）。不崩溃，但**日志过滤失效**。

**建议（保持功能不变）**：分类名做成 `Log` 的常量（`Log.CAT_SLEEP := "睡眠"`），
调用点改成 `Log.ev(Log.CAT_SLEEP, ...)`。**或者**更省事：把默认值改成 `false` +
未知分类时 `push_warning` —— 这样拼错立刻可见。

## 八、审计的局限（说清楚，免得当成全面保证）

1. **只做了静态扫描 + 定点阅读，没跑起来验证行为**。所有结论都附了文件行号，可复核。
2. **性能只做了静态判据**（skill 的 `_process` 体量 / 帧内重操作 / 缓存引用），
   **没有跑 Godot Profiler**。项目当前的规模（8 只生物 + 130×130 格）不太可能有问题，
   但如果要出正式结论，应该跑一次 60 秒的 Profiler 基线。
3. **"重复字面量"的自动检测只对字符串可靠**。数字部分（`1.0` 出现 7 次之类）**基本都是巧合**——
   不同概念恰好同值，**不是**同值复制。我逐条核过，只有 §S1 那三个字符串是真的。
4. **没审计美术资源与 `.import` 设置**（不在本次范围）。
