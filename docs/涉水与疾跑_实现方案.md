# 涉水修复 & 疾跑系统 —— 实现方案

> 本文回答两个问题：**① 人怎么能往水里走**（诊断 + 修法）、**② 疾跑状态设计**（人按 Shift ×2 速度、疲劳快拉、有体力池；动物同样有，用于逃命）。
> 状态：**待评审**，尚未动任何逻辑代码。
> 诊断数据来源：2026-09-20 headless 实测（种子 20260918）。

---

## 〇、诊断结论（先看这个）

### 问题①「人怎么能往水里走」——**根因是视觉，不是逻辑**

实测数据（`--headless` 跑 main.tscn，种子 20260918）：

| 项 | 实测值 |
|---|---|
| 全图 | 130×130 = 16900 格 |
| 未知（黑地） | **16557 格（97.97%）** |
| 草原 | 272 格 |
| 高草 | 71 格 |
| 水域 | **447 格** |
| 主角出生点 | **(96, 49) → 地形 = 未知，walkable = true** |
| 8 只猪出生点 | 全部 = 未知（黑地） |
| 推进 900 游戏分后站在水格上的生物 | **0 只** |

三条结论，逐条对应代码：

**1. 逻辑上确实进不去水。** `GridMover.is_cell_free()` 第 21 行明确调了 `Terrain.walkable(cell.terrain)`，而 `Terrain.WATER` 的 `walkable = false`。玩家大脑 `PlayerBrain` 与 AI 大脑 `Brain` 的每一步都经过 `GridMover.try_step()` → `move_to()`，没有旁路。推进 900 游戏分、9 只生物的实测结果也是 0 只踩水。

**2. `水` 与 `黑地` 在主画面上**像素级完全一样**。** 这是真凶：

```gdscript
# world/terrain.gd
UNKNOWN: { "texture": null, "color": Color(0.0, 0.0, 0.0), "walkable": true  }
WATER:   { "texture": null, "color": Color(0.0, 0.0, 0.0), "walkable": false }
```

`MapRenderer._draw()`（第 44–48 行）的口径是「有图用图，无图用 color 兜底」——两者都 `texture == null`、都 `color == 纯黑`，于是画出来**每个像素都相同**。区分它们的唯一线索是 `WaterLayer` 烘的那条 **1px 岸线**。

而世界 **97.97% 是黑地**（可以踩），只有 2.6% 是水。于是玩家的真实体验是：

> 在一大片纯黑上走 → 看到一条白线 → 线里面还是纯黑 → **以为白线就是水、里面也是水** → 心想「我怎么走进水里了」。

反过来也成立：玩家站在黑地上（合法），但**他以为自己站在水里**。**两种情况下画面完全一致，所以从用户视角看，这是一个无法自证的真 bug。**

**3. 顺带发现一个真的会出事的隐患（目前不可达，但是颗雷）。**

`GridManager._free` 在 `_ready()` 里对**全部 16900 格**初始化（第 36–37 行），`occupy`/`release` 只改 `content`，**从不问 `terrain`**。同时：

```gdscript
# main.gd:373
func spawn_pig_random() -> void:
	var c := GridManager.random_free_cell()   # ← 不查 walkable
	_spawn_pig(c)
```

`Creature.can_place_at()`（第 245–251 行）也**只查「界内 + 没人占」，不查 terrain** —— 所以 `coord =` 直写（`main.gd:172/235`）或 `move_to()` 都**不设防**。

```gdscript
# creature/creature.gd:245
func can_place_at(c: Vector2i) -> bool:
	if not GridManager.in_bounds(c.x, c.y): return false
	var cell := GridManager.cell_at(c.x, c.y)
	if cell == null: return false
	return cell.content == null or cell.content == self     # ⚠ 没有 Terrain.walkable
```

**当前安全性完全依赖"每个调用方都自觉先过滤地形"** —— `_free_adjacent`（第 299 行）、`_pick_free_near`（第 312 行）、`_player_spawn_cell`（第 229 行）各自手写了一遍 `Terrain.walkable(cell.terrain)`。**这是一处"同一条规则抄了四遍、而唯一把关的那遍漏了"的典型耦合债。** 今天没爆，只是因为 `spawn_pig_random()` 目前**没有任何调用点**（全库 grep 确认只有定义、无调用；注释里说「调试工具栏「刷猪」用」，但那个工具栏不存在/已删除）。一旦有人把它接上按钮，猪就会直接落进湖里。

### 问题②「疾跑」——从零开始，三样东西都没有

全库 grep `sprint|疾跑|体力|stamina` → **零命中**。实测确认：

| 需要的东西 | 现状 |
|---|---|
| `sprint` 输入动作 | **不存在**（`project.godot` 只有 `move_up/down/left/right`） |
| 体力/耐力需求 | **不存在**（只有 `food`/`water`/`warmth`/`fatigue`） |
| 动物感知威胁 | **不存在**（`Perception.neighbors()` 过滤条件是 `cr.def == creature.def` —— **只看得见同物种**） |

最后一条是设计上最要紧的：用户说「动物可以更快逃离危险」，但**现在没有任何代码知道"危险"是什么**。所以方案里必须明确"逃命的触发从哪来"，否则疾跑给动物加了也是死代码。

## 一、问题①：涉水修复

### 1.1 修法决策：**改视觉，不改逻辑**

逻辑是对的（水就是不能踩），错的是**表现没能把"能踩的黑地"和"不能踩的水"区分开**。所以修的是表现层。

**不要做的**（都是治标或引入退化）：
- ❌ 把 `Terrain.UNKNOWN` 改成可踩的浅灰色 → 会毁掉整套 DF 式"黑底"美术基调。
- ❌ 让 `Creature.move_to()` 补上地形检查 → **看起来**更安全，但它会把一个「表现问题」掩盖成「逻辑问题」，而且 `coord =` 直写式出生仍然绕过它。真要加固得见 §1.3。
- ❌ 把水格从 `_free` 里剔除 → 会让 `free_count()` 之类的语义分叉，且没解决"看不出来"。

**要做的**：给水一个**能一眼认出的内部**。三选一，建议 **A + C 组合**：

| 方案 | 做法 | 代价 | 评价 |
|---|---|---|---|
| **A. 水填深蓝**（推荐） | `WATER.color` 从 `(0,0,0)` 改成深蓝（如 `Color(0.06, 0.12, 0.22)`），或在 `world/art/` 加一张 `water.png` 走「有图用图」 | 一行数据；与用户此前"水不填色"的拍板**冲突** | ✅ 最直观，一眼就分得开。**需要用户重新拍板** |
| **B. 黑地区分度** | 给 `UNKNOWN` 一个极暗但仍可辨的纹理/色（如 `(0.05,0.05,0.05)` + 噪点） | 改动美术基调，黑地不再纯粹 | ⚠️ 可行，但"黑地"本来就是这个世界的主体，改了影响面大 |
| **C. 岸线加粗 + 水侧内阴影**（推荐叠加） | `lake_common.tres` 的 `edge_width_px` 1 → 2；或让 `WaterLayer` 在水侧再画一圈半透明暗带 | 改 `WaterLayer`，需新画法 | ✅ 保住"水不填色"的拍板，同时把边界说清楚 |
| **D. 玩家/生物在岸边给个提示** | HUD 显示脚下地形 | 治标 | ❌ 玩家不该靠读 HUD 才敢走路 |

> ⚠️ **这一条必须问用户**：`Terrain.WATER` 的注释写着「**【用户拍板】水不填色**：湖里湖外都是黑，只有岸线由 WaterLayer 画出来」——方案 A 直接推翻这个拍板。所以 §1.1 的取舍要用户定；我倾向 **A**（体验优先于"两侧同色"的美学洁癖），**C** 作为不推翻拍板的备选。

### 1.2 顺带修：`unknown` 的语义

`Terrain.UNKNOWN` 的 `label` 是「未知」，`walkable` 是 `true`。**"未知"可以踩，这个语义本身是自洽的**（它是"还没被地形生成器覆盖的黑土"），但玩家读日志/看检视面板时会困惑。建议 **label 改成「黑土」或「荒地」** —— 一个字的信息量差异，但对"我到底站在哪"的理解完全不同。纯数据改动，零风险。

### 1.3 加固：把「不可踩的格」从 `_free` 里剔除（可选，但建议做）

虽然 `spawn_pig_random()` 目前不可达，但它是颗雷。**修法放在 `GridManager`，让"唯一事实来源"自己保证一致性**：

```gdscript
# common/grid/grid_manager.gd
## 某格是否"可落脚"：空格 AND 地形可踩。**所有"随机挑一格放东西"都必须走这里。**
func is_placeable(c: Vector2i) -> bool:
	if not in_bounds(c.x, c.y): return false
	var cell := grid.get_cell(c)
	if cell == null or cell.content != null: return false
	return Terrain.walkable(cell.terrain)

## 随机挑一个**可落脚**的格（原 random_free_cell 的语义修正版）。
func random_placeable_cell() -> Vector2i:
	# 地形只在启动时写一次，故 `_free ∩ walkable` 可以缓存
	...
```

以及把 `Creature.can_place_at()` 补上地形检查：

```gdscript
func can_place_at(c: Vector2i) -> bool:
	if not GridManager.in_bounds(c.x, c.y): return false
	var cell := GridManager.cell_at(c.x, c.y)
	if cell == null: return false
	if not Terrain.walkable(cell.terrain): return false   # ← 新增：出生/直写坐标也不许进水
	return cell.content == null or cell.content == self
```

**风险提示**：加了这一条之后，**所有"把生物放到某格"的调用方如果传了水格，会从"静默落进去"变成"拒绝生成"** —— 这正是在 `_ready()` 里 `if not can_place_at(coord): _fail_init(...)` 想要的行为（宁可不出生，也不要一个站在湖里的猪）。但**必须回归验证**：`_player_spawn_cell` / `_free_adjacent` / `_pick_free_near` 都已经过滤了地形，理论上不受影响；`_spawn_offspring` 里 `_pick_free_near(mother.coord, 1, 3, rng)` 若在湖边失败会 fallback，也要确认 fallback 分支也过滤了地形（第 357–362 行：`c_at.x < 0` 时会用 `_pick_free_near(center, ring_in, ring_out, rng)`，这个也过滤了 ✓）。

### 1.4 `GridMover.is_cell_free` 的注释纠错

第 22 行注释写「将来**水面**/岩壁才会拦」——**水面已经拦了**，而这句注释正是"看起来没拦"的误导源头之一。改成事实描述。

### 1.5 验收清单

| # | 验收项 | 判据 |
|---|---|---|
| 1 | 玩家站在黑地上时，能明确分辨"这是黑土"而非"这是水" | 窗口截图人工确认 |
| 2 | 玩家朝水走，会被挡住且**能看懂是被什么挡住** | 走到岸边停下，画面给出明确"这里是水"的信号 |

## 二、问题②：疾跑 / 体力系统

### 2.0 设计目标（从用户原话拆解）

> 「人是按 shift 就能快两倍 但疲劳会拉很快 然后有段时间的体力值 这样动物可以更快逃离危险」

| # | 需求 | 落地为 |
|---|---|---|
| R1 | 按住 Shift → 约 **2×** 速度 | 疾跑时步频翻倍（`gate` 减半） |
| R2 | 疾跑时**疲劳拉得很快** | 体力快速消耗；体力映射到既有的 `fatigue` 需求 |
| R3 | **有段时间的体力值** | 一个**可耗尽的体力池** + 耗尽后**一段时间无法再冲刺**（恢复期） |
| R4 | 动物也有疾跑 | 同一套组件，挂在猪上 |
| R5 | 动物用它**逃命** | 需要一个"威胁"信号源（当前不存在，见 2.4） |

### 2.1 关键设计决策：**复用 `fatigue`，不新开一条需求**

**决策：不新增 `stamina` 需求，而是把"体力"做成 `Needs.fatigue` 之上的一层。**

理由 —— 这是本项目"**同一事实只有一个定义域**"纪律的直接应用（见 `brain.gd` 第 306–316 行那段血泪注释：曾经 `Brain` 和 `PlayerBrain` 各算一套减速，调一个系数两边朝不同方向漂移）：

- 项目里**已经有** `fatigue`（`need_fatigue.tres`，max 100，drain 0.03472，**非致命**）。
- 项目里**已经有** `Needs.move_speed_factor()`（协议 6）：`lerpf(0.55, 1.0, fatigue_ratio)` —— 累到 0 → 只剩 55% 速度。
- 项目里**已经有** `Brain` 的 rest 驱动 + `SLEEP_RECOVER_RATE` 恢复疲劳。
- 再开一个 `stamina` 需求 = **第二条"累"的轴**，玩家面板要画两行意思相近的条，`Brain` 要判断两个"累不累"，将来调平衡要同时调两处。**这是债，不是功能。**

**所以**：新增的 `Sprint` 组件**读写既有的 `fatigue` 需求**，它自己只负责"**能不能冲刺**"+"**冲刺时的消耗倍率**"，不自己存第二份数值。

### 2.2 新组件：`creature/components/sprint.gd`

一个新组件，走项目现有的 `CreatureComponent` 协议，**不新增协议**。

```gdscript
class_name Sprint
extends CreatureComponent

## 疾跑组件（2026-09-20）。
##
## 【它管什么】"现在能不能冲刺" + "冲刺时消耗多少"。
## 【它不管什么】
##   - **不自己提速**：速度走协议 6（move_speed_factor），与 Aging/Body/Needs 同一个出口。
##   - **不自己存体力条**：体力 = 既有的 `fatigue` 需求（见 §2.1 的设计决策）。
##   - **不管往哪跑**：那是 Brain / PlayerBrain 的事。
##
## 【为什么挂在组件上而不是写进 Creature】猪需要它、人也需要它，
##   而"是不是疾跑中"是**可查的事实**（协议 3 的 debug_state 要报、将来动画要读），
##   不是某一次调用的参数 —— 所以它得是个有状态的组件，不是工具函数。

const FATIGUE_ID := "fatigue"          # 与 Needs / Brain 用同一个 id（别再散写字符串）
const SPRINT_FACTOR := 2.0             # 用户拍板：快两倍
const MIN_FATIGUE_TO_START := 0.15     # 体力比例低于此值**起不了步**（但已经在跑的不打断）
const MIN_FATIGUE_TO_KEEP := 0.02      # 跑到这个值以下**强制脱力**
const EXHAUST_LOCKOUT_MIN := 30.0      # 脱力后强制冷却（游戏分）——「然后有段时间的体力值」
const SPRINT_DRAIN_MULT := 6.0         # 冲刺时疲劳消耗倍率（用户："疲劳会拉很快"）
```

> ⚠ **上面这段是本方案第一版的草图，其数值已全部作废**，保留只为记录当时的推理过程。
> 实际落地见 §2.7 —— 冲刺消耗最终是**独立绝对值 `DRAIN_PER_SEC = 1.0`**，
> 冷却也从 30 改成 **5 秒**。**"倍率"这条路被证明是错的**，原因见 §2.7。

```gdscript
var _sprinting := false
var _lockout := 0.0                    # >0 = 冷却中，不能起跑

## 每帧推进冷却与强制脱力。
func tick(dt: float) -> void:
	if _lockout > 0.0:
		_lockout = maxf(_lockout - dt, 0.0)
		_sprinting = false
		return
	if _sprinting and _fatigue_ratio() <= MIN_FATIGUE_TO_KEEP:
		_stop(true)                    # 跑空了 -> 强制脱力 + 进冷却
	elif _sprinting:
		# 冲刺消耗：直接抬疲劳的衰减（走 Needs 内部累加器，不另存数值）
		_drain_extra(dt)

# ---------------- 对外 ----------------
## 请求冲刺（每帧由大脑调用）。返回**实际是否在冲刺**。
func request(on: bool) -> bool: ...
func is_sprinting() -> bool: return _sprinting
func is_locked_out() -> bool: return _lockout > 0.0

# ---------------- 协议实现 ----------------
## 协议 3：调试自述
func debug_state() -> String: ...
## 协议 6：疾跑时提速
func move_speed_factor() -> float:
	return SPRINT_FACTOR if _sprinting else 1.0
```

**协议 6 的钳制问题（必须处理）**：`Creature.locomotion_speed()` 会把所有 `move_speed_factor()` **相乘后钳到 0..1**。疾跑要**超过 1.0**，所以现在这个钳制会**把疾跑吃掉**。两种改法：

| 改法 | 做法 | 评价 |
|---|---|---|
| **(a) 拆成两条协议** | 保留协议 6 为"减速"（相乘、钳 0..1），**新增协议 8 `sprint_speed_factor()`**（相乘、钳 1..N），最后 `locomotion = clamp(slow, 0, 1) * clamp(sprint, 1, MAX)` | ✅ 语义干净：减益与增益分开，各自有自己的天花板；不会出现"两条减益相乘意外把增益抵消" |
| (b) 放宽钳制到 0..2 | `locomotion_speed()` 上限改 2.0 | ⚠️ 最小改动，但一条失控的减益/增益就能把速度推到 2 倍，**没有隔离** |

**建议 (a)**。这也符合项目"协议即插槽"的风格（`creature_component.gd` 已有 7 条协议，加第 8 条是既定演进方式）。

### 2.3 玩家侧：Shift 输入

**`project.godot` 新增 `sprint` action**：
- 物理键：**Shift**（`physical_keycode = 4194325` = `KEY_SHIFT`）
- ⚠️ **必须用 `physical_keycode`**，与现有四个 move action 一致（第 56 行注释：与键盘布局无关）。

`PlayerBrain.read_sprint()` —— **刻意不做成 `Input.get_vector` 那样的自动路由**，而是独立一次查询：

```gdscript
func read_sprint() -> bool:
	return Input.is_action_pressed("sprint")
```

然后 `PlayerBrain._submit()` 里：

```gdscript
var sprint := creature.get_component(Sprint) as Sprint
var sprinting: bool = sprint != null and sprint.request(read_sprint())
```

**为什么"按住才跑"而不是"按住一次切开关"**：用户原话「人是按 shift 就能快两倍」= **按住**（`HOLD` 语义，与 `PlayerBrain.HOLD_MOVE` 一致）。松手立刻回常速。

**步频**：`gate = move_interval / locomotion_speed`，locomotion 翻倍 → **gate 减半 → 每格耗时减半 → 速度翻倍**。**无需改 `_gate_seconds`**，协议 6/8 自动生效。这正是既有架构的好处。

### 2.4 动物侧：**"危险"从哪来** —— 这是本方案最需要用户拍板的一处

需求 R5 说动物要"更快逃离危险"。但实测确认：**`Perception.neighbors()` 只返回同 `def` 的邻居**（`perception.gd` 第 ~20 行），所以猪**根本看不见人**。

```gdscript
# creature/components/perception.gd（现状）
## 过滤：同物种（同一个 def 资源引用）+ 活着 + 没藏起来
```

**所以必须新增一个"威胁感知"信号，否则动物疾跑是死代码。** 三个选项，**代价与玩法差异极大**：

| 方案 | 做法 | 代价 | 玩法效果 |
|---|---|---|---|
| **T1. 玩家=威胁（最小可用）** | `Perception` 加一个 `threats()`：把**在 `"player"` 组里的生物**、且在半径内、且当前**不在隐蔽状态**的算作威胁 | 小。组标已存在（`main.GROUP_PLAYER`），`is_concealed()` 已存在 | ✅ 立刻可玩：靠近猪 → 猪加速跑开。**但"人一进高草猪就看不见你"这条隐蔽玩法被自动激活** —— 这其实很妙 |
| **T2. 通用威胁协议** | 新增一条"谁是威胁"的判定协议，将来食肉动物/火/其他物种都能挂 | 中 | 为将来食肉动物留好接口，但现在**没有食肉动物**，会写成过度设计 |
| **T3. 不做威胁，只给动物"随机冲刺"** | 动物闲时偶尔冲刺 | 极小 | ❌ 不满足用户"逃离危险"的原意，等于没做 |

**建议 T1**，理由：
1. 它把"玩家"和"危险"这两个用户语境里的东西**用现成的机制**接上了（`"player"` 组标 + `is_concealed()`），零新概念。
2. 它顺带让**隐蔽系统第一次有了玩法后果** —— 此前 `Concealment` 只是画面上让生物半透明，没有任何行为差异。现在"藏进高草 → 猪看不见你 → 猪不再逃"是真正的潜行机制。
3. T2 的通用化可以等真有食肉动物时再做，**现在做就是猜**。

**但注意 T1 的一个副作用**：玩家一开局就会把周围的猪全吓跑。要在纸上先定好：
- 威胁半径（建议 = `Perception.radius`，现为 6 格）；
- 猪是"**逃向远离玩家的方向**"（`Bayes` 里已有 `_dir_from_nearest` 的实现可复用，见 `brain.gd:288`）；
- 逃命时 `rest`/`idle`/`feed` 权重应当被**压制**（否则会出现"被追着还站在原地睡觉"的滑稽场面）。建议在 `Brain` 里加一个 `flee` 驱动，权重由威胁强度决定，且**压过 rest**。

### 2.5 `Brain` 侧的接线（动物）

`Brain._decide_and_act()` 里新增一个驱动 `flee`：

```gdscript
# 威胁（可选组件 Perception + Sprint）
var flee_w := 0.0
var flee_dir := Vector2.ZERO
if sprint != null and sprint.is_locked_out() == false:
	var threats := perc.threats()          # 新方法，见 §2.4 T1
	if not threats.is_empty():
		flee_w = FLEE_GAIN                  # 要压过夜间 rest（数值上 > NIGHT_REST_BONUS）
		flee_dir = _dir_from_nearest(threats)
```

`drives` / `weights` 数组各加一项。`match chosen` 里加：

```gdscript
"flee":
	if _step_toward(mover, dirs, flee_dir):
		sprint.request(true)              # 逃命时真的冲刺
		last_drive = "flee"
	else:
		_wander_step(mover, dirs)
```

**逃命时是否冲刺**：建议「**威胁在半径内 → 冲刺；体力见底 → 只能常速逃**」。后者由 `Sprint.is_locked_out()` 自动处理，`request()` 会返回 `false`，猪就变成常速跑 —— **"追累了咬死"的玩法自然成立**。

**性能注意**：`flee` 的威胁查询如果每只猪每帧都做，代价 = O(生物数)。但 `Brain` 是**按决策间隔**调用的（`_timer` 到点才决策一次），不是每帧。**但 `Sprint.tick(dt)` 是每帧的** —— 所以 `_drain_extra` 必须是 O(1)（只读一个需求）。威胁查询放在决策里（低频），✓。

### 2.6 UI：把体力显示出来

用户说「然后有段时间的体力值」—— **必须看得见，否则玩家不知道自己在消耗什么**。

- **`ui/player_hud.gd`**：`NEED_COLS` 已在上一轮改成 2。`fatigue` 那一行**加一个"冲刺中/脱力中"的标记**（文字或颜色），并让条在冲刺时**变成醒目色**。
- **`ui/player_panel.gd`**：`fatigue` 行同理；`_needs` 分区已有（`_rebuild()` 里按 `active_needs` 建行），加一个状态后缀即可。
- 建议**不新增 UI 元素**，只在既有 fatigue 行上叠加状态 —— 保持"同一事实只有一个显示域"。

### 2.7 需要调的数据（`need_fatigue.tres`）—— **已定案：DRAIN_PER_SEC，改后不写倍率**

现在 `drain_rate = 0.03472` / 游戏分 → 满 100 跑到 0 需要 **2880 游戏分 = 2 游戏天**。这显然不能当"体力池"用。

**两种设计**（需拍板）：

| 设计 | 做法 | 体感 |
|---|---|---|
| **S1. 只加冲刺消耗，正常衰减不动** | 冲刺用**独立绝对速率**；正常衰减一个字不动 | ✅ 不动既有平衡（猪的时间账极其脆弱，见 `brain.gd` 里那几段实测注释）|
| **S2. 重做 fatigue 曲线** | 把 `drain_rate` 调大、max 调小 | ❌ **高危**。`fatigue` 同时被 `Brain` 的 rest 时长、`Needs.move_speed_factor` 的减速读取。改它会连带影响**猪的整个决策时间账**（那几段注释显示：调错会直接导致全员饿死/渴死） |

**→ 采用 S1。但 2026-09-20 落地时发现 S1 的"叠在既有衰减上"有第二种写法，而第一版写错了。**

#### 踩到的坑：把冲刺写成"基线的 N 倍"

第一版照着"用户说 2~3 倍"写成 `SPRINT_DRAIN_MULT = 2.5`（即 `drain_rate × 2.5`），结果：

```
冲刺速率 = 0.03472 × 2.5 = 0.0868 点/分
满体力可跑 = 100 / 0.0868 ≈ 1152 游戏分 ≈ 19 分钟
```

**而用户举例是"能跑 10 秒"—— 差了整整两个数量级。**

#### 根因：**"同一根槽"不等于"同一把尺子"**

| 用途 | 为谁而调 | 满槽时长 |
|---|---|---|
| 疲劳基线 `0.03472` | **猪的作息**（睡一觉顶一整天）| **2.00 游戏日** |
| 冲刺消耗 | **玩家的手感**（10 秒爆一下）| 期望 **10 秒量级** |

两者差 **28.8 倍**。硬用一个乘数绑住，必然有一方被毁：
若为让冲刺 10 秒见底而把基线涨到 0.4，疲劳槽只剩 250 分（4.2 真实分钟）→ 猪一天累垮 5.8 次、作息全崩。

#### 正确做法：冲刺速率是**独立绝对值**

```
const DRAIN_PER_SEC := 1.0     # 点/游戏分（= 点/真实秒）
```

- 走路/站着的消耗仍归 `need_fatigue.tres`（**一个字没动**）
- 冲刺的消耗归 `DRAIN_PER_SEC`

**共用一根槽（存储）+ 各用一把尺（速率）—— 两者不矛盾。**
用户"跑步比走路快得多"的直觉依然成立，只是这个比值从此是**结论**（`1.00/0.03472 ≈ 28.8`），不再是**输入**。
好处：**想调手感只改 `DRAIN_PER_SEC` 一个数，绝不会牵动猪的作息。**

#### 最终数值

| 项 | 值 |
|---|---|
| 满体力可跑 | `(100 − 100×0.02) / 1.0` = **98 真实秒**（≈ 392 格）|
| 体力 90 可跑 | **88 秒** = 满值的 **89.8%** ← 与用户"10→9 秒"（0.900）比例一致 ✓ |
| 冲刺 / 走路 速率比 | **28.8 倍** |
| 脱力冷却 | **5 秒**（由 30 改小 —— 跑 98 秒才脱力，罚 30 秒不成比例）|

**顺带一个数值问题**：`SPRINT_FACTOR = 2.0` × `MIN_SPEED` 保护 —— `PlayerBrain._gate_seconds()` 里 `mi / maxf(speed, 0.15)`，主角 `move_interval = 0.5`，满状态 `locomotion ≈ 1.0` → gate 0.5s/格。冲刺 → gate **0.25s/格**。**手感是"快一倍"，符合用户"快两倍"**（速度翻倍 = 耗时减半）。✓
