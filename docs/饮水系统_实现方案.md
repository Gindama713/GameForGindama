# 饮水系统 · 设计与实现规划（Drinking / Thirst）

> 状态：**规划草案（未实现）**，供评审后再动手。作者 · 2026-09-20
> 唯一事实基准仍是 `docs/事实文档.md`；本文件描述「打算怎么做」，落地后回写进事实文档。
> 设计准绳：数据驱动、组件协议解耦、`TimeSystem` 固定 tick、可复现 RNG、只新增少改动、不提前抽象。

---

## 0. 一句话与三条核心判断

**给猪加"喝水"：渴了 → 走到最近的湖岸 → 站在岸边把 `water` 需求补回来。**

1. **这不是"加新功能"，是补一个已经存在的必死 bug。**
   实测（`TimeSystem.speed=300` 加速跑，7 只猪）：**7/7 全部死于「口渴 耗尽」**，
   首例在开局后 **1430 游戏分（≈0.99 游戏日）** —— 与 `100 ÷ drain_rate(0.07) = 1429` 完全吻合。
   也就是说：**草给的那点水（每口 +2）实际贡献 ≈ 0**，而口渴是致命的（`depleted_is_lethal = true`）。
2. **水的"不可踩"决定了整个设计的形状。**
   `Terrain.walkable(Terrain.WATER) == false` → 猪**永远站不到水格上**。
   于是「能喝到」= **与自己 4 邻接的格里有水域格**；「去哪喝」= **与水邻接的可走格（下称"岸格"）**。
   ⚠ 这跟吃草（站在草格**上**）是**不同**的几何关系，**不能照抄 `Grazing`**。
3. **一行代码都不用碰生死内核。**
   渴死这条路**早就通了**：`NeedDef.depleted_is_lethal` → `Needs.is_lethal()` →
   `Creature.check_dead_state()` → `die()`。本系统只负责"把水补回来"，
   **不改 `die()`、不改 tick 循环、不改 `NeedDef`/`Needs`**。

## 1. 现状分析：代码关联关系

### 1.1 四层与"谁认识谁"

| 层 | 是谁 | 对下层的态度 |
|---|---|---|
| **世界底座**（Autoload） | `GridManager`（130×130 网格 + 派生索引）· `Terrain`（地形注册表）· `WorldSeed` · `TimeSystem`（时钟）· `EventBus`（信号）· `DefValidator` | 不认识生物 |
| **世界服务** | `GrassField`（**活草**：耐久/再生/扩散）· `LakeGenerator`→`WaterLayer`（水与岸线） | 不认识生物；只被查询 |
| **生物层** | `Creature`（基类，**只认组件协议**）+ 11 个组件 | 组件调服务；**服务不知道组件存在** |
| **表现层** | `MapRenderer` · `Minimap` · `CameraRig` · `CreatureInspector` | 读服务/订阅 `EventBus`，不反向驱动逻辑 |

关键解耦规则（本系统必须遵守）：
- `Creature` 基类**不许出现具体组件类名**，只遍历协议（`is_lethal()` / `allows_movement()` / `is_concealed()` / `debug_state()` / `visual_scale()`）。
- 组件之间**不许互相 `get_component`**……实际上 `Brain` 会读 `Grazing`/`Personality`/`Perception`/`Aging`/`Lineage` 的**只读钩子**（这是既有做法），
  但一律是"缺了也能跑"的**可选读取** —— `Drinking` 要沿用这个姿势。
- 服务不认识生物：`GrassField` 只提供 `bite()/is_edible()/...`，**它不知道猪是什么**。

### 1.2 猪当前的状态与行为链（一次 tick）

```
TimeSystem.tick(dt)  ──►  Creature._on_tick(dt)
                             ├─ for comp in 组件: comp.tick(dt)      # 11 个组件各自推进
                             ├─ _refresh_growth_scale()              # 年龄成长刷精灵缩放
                             └─ check_dead_state()                   # 唯一"问一次生死"的地方
                                  └─ 任一组件 is_lethal() → die()
```

| 组件 | 干什么 | 与"喝水"的关系 |
|---|---|---|
| `GridMover` | 能不能移 / 执行移动（`free_directions()` / `try_step()`） | **执行**"朝水走一步" |
| `Brain` | 加权随机（轮盘）在 7 个驱动里挑一个 | **要找它加第 8 个驱动 `drink`** |
| `Needs` | 需求衰减 + `restore(id, amount)` | **喝水的目的地**（`restore("water", ·)`） |
| `Grazing` | 站嫩草上按节奏咬 → `GrassField.bite` + `restore("food"/"water")` | **模板**（但几何关系不同，见 §0.2） |
| `Perception` | 半径内邻居 | 不参与 |
| `Concealment` | 站在高草 = 隐身 | 岸格可能就是高草（边界 §5.11） |
| `Aging` / `Lineage` / `Reproduction` | 年龄/血统/繁殖 | 幼崽速度更慢 → 高风险（边界 §5.6） |
| `Body` / `Personality` | 部位血量 / 六维性格 | 性格调权重（`energy` 等） |

`Brain` 当前 7 个驱动与"体重"（占位值）：

| 驱动 | 权重公式 | 白天典型值 | 夜里典型值 |
|---|---|---|---|
| wander | `0.35 + 活力×0.5` | ≈0.6 | ≈0.6 |
| social / separate | 有邻居时 = 合群度 / (1−合群度) | 0~1 | 0~1 |
| rest | `(1−活力)×0.5 + (1−疲劳)×0.8` **+ 夜里 3.0** | ≈1.05 | **≈4.05** |
| idle | `0.35 + (1−活力)×0.6` | ≈0.65 | ≈0.65 |
| feed | `饥饿度 × 4.0`（且附近有嫩草） | 0~4.0 | 0~4.0 |
| cling | 幼崽离妈 ≥2 格时 3.0 | 0 或 3.0 | 0 或 3.0 |

> **读出来的关键约束**：夜里 `rest ≈ 4.05` 是最强的竞争者。想让"渴到快死了"的猪**不再睡觉**，drink 权重必须能超过 4.05。

### 1.3 口渴这条线现在断在哪（算术 + 实测）

| 项 | 值 | 出处 |
|---|---|---|
| 口渴 max / drain | 100 / **0.07** 每游戏分 | `creature/pig/data/need_water.tres` |
| 饥饿 max / drain | 100 / **0.05** 每游戏分 | `need_food.tres` |
| 满→空（口渴） | **1429 游戏分 ≈ 0.99 游戏日 ≈ 23.8 真实分钟** | 100 ÷ 0.07 |
| 满→空（饥饿） | 2000 游戏分 ≈ 1.39 游戏日 | 100 ÷ 0.05 |
| 草补水·理论峰值 | 每口 +2 / 间隔 8 分 = **0.25** 每游戏分 | `grass_common.tres` + `grazing.gd` |
| 草补水·**实际可持续** | **0.02** 每游戏分（`Grazing` 维持"饱"只需每 100 分咬一口 → 2 ÷ 100） | `SATIETY_STOP = 0.95` |
| **净变化** | 0.02 − 0.07 = **−0.05 / 游戏分** | 推导 |
| **实测（加速 300×）** | **7/7 死于「口渴 耗尽」，首例 1430 游戏分** | 探针 `_probe_thirst` |

结论：**口渴永远先于饥饿要命（0.07 > 0.05），而草补的那点水根本不够。**
把"喝水"做出来，是让这批猪能活过第二天的**前提**。

## 2. 设计

### 2.1 触发条件

新增组件 `creature/components/drinking.gd`，常量（占位，待调）：

| 常量 | 建议值 | 含义 |
|---|---|---|
| `THIRST_ID` | `"water"` | 用哪个需求当口渴（别散写字符串，仿 `Brain.FATIGUE_ID`） |
| `WATER_STOP` | `0.95` | 比例 ≥ 此值就停（与 `Grazing.SATIETY_STOP` 对称） |
| `DRINK_GAIN` | `5.0` | 权重系数（略高于 `FEED_GAIN=4.0`：渴得更快，且水不能边走边补） |
| `THIRST_PANIC` | `0.20` | 低于此比例 = 危险档 |
| `DRINK_PANIC_BOOST` | `1.6` | 危险档权重再乘它 → **保证压过夜间 `rest≈4.05`** |
| `DRINK_RATE` | `1.5` | 站在岸边每游戏分补多少（≈67 游戏分补满） |
| `WATER_SEARCH_RADIUS` | `80` | 觅水半径（格）。**因为查询是对"水格表"遍历，代价与半径无关**，可以给大 |
| `ADJACENT_DIAGONAL` | `false` | 斜对角算不算"在水边" → **已拍板：只认 4 邻**（本项保持 false） |

权重曲线（`w = (WATER_STOP − ratio) / WATER_STOP × DRINK_GAIN`，危险档再 ×1.6）：

| 口渴比例 | 权重 | 对比 |
|---|---|---|
| 0.90 | 0.53 | < 游荡(0.6) → 不太渴，不打扰 |
| 0.70 | 1.32 | 略压过白天发呆/短歇 |
| 0.50 | 2.37 | 明显高于白天一切（除 feed） |
| 0.30 | 3.42 | 与 feed 峰值(4.0) 同级 |
| 0.19 | 4.02 ×1.6 = **6.43** | **> 夜间 rest(4.05)** → 渴到危险会起床找水 |
| 0.05 | 4.74 ×1.6 = **7.58** | 最高优先 |

设计意图（"涌现"而非写死）：**不太渴时该干嘛干嘛；渴到一半开始分出精力找水；渴到危险会不顾夜里该睡觉。**
这套"起床喝水"不是硬编码的 if，而是权重自然竞争的结果 —— 与项目 `Brain` 的既有哲学一致。

### 2.2 数值变化（喝水的模型）

**推荐：连续吸（不是离散大口）**

理由：草用"一口一口"是因为草有**耐久**（有限、可被吃秃）；水是**无限源**，
再搞一套计时器是多余的机械。且 `Brain._recover_while_resting()` 已经用"连续回复"的先例。

```
Drinking.tick(dt):
    if 不渴:            return
    if 不在水边:         return
    Needs.restore("water", DRINK_RATE * dt)      # 唯一数值入口，已存在
```

- 补满 0→1.0 需 `100 ÷ 1.5 ≈ 67 游戏分 ≈ 1.1 真实分钟`（站着不动一会儿，观感合理）。
- 比例到 `WATER_STOP(0.95)` 自然停（`wants_water()` 返回 false）。
- `Needs.restore` 本身会 `minf(value + amount, max_value)` → 不会溢出。
- `[已拍板 A]` **不采用**离散大口（`DRINK_INTERVAL 6` 分/口、`+9`）。选连续吸的理由：水是无限源、没有"耐久"要记；少一套计时器；`Brain` 已有"睡觉连续回疲劳"的先例。

### 2.4 觅水（查询）—— 唯一需要动"世界底座"的地方

**推荐：在 `GridManager` 加一个通用派生索引**（与既有 `_free` 派生自 `content` 同一套路数）：

```
GridManager:
    var _terrain_cells: Dictionary      # terrain_id -> PackedVector2Array（格坐标）
    _ready(): EventBus.terrain_changed.connect(_rebuild_terrain_index)
    nearest_cell_with_terrain(from, max_radius, id) -> Vector2i     # 没有 → (-1,-1)
```

- 重建代价 O(16900)，本局只在启动时触发一次（地形只在启动时写）。
- 查询代价 **O(该地形的格数)**（本局 363 格）→ **与半径无关**，所以半径可以给到 80。
- 为什么放这里："哪里是某种地形"是**网格域**的事实，`GridManager` 已经持有派生索引先例；
  而且是**通用**的（将来的寻矿 / 寻火 / 寻药都能用），不是给猪专用的补丁。

被否掉的两个备选：
- ❌ **新建 `WaterField` Autoload**：会把"水在哪"变成**第二份事实来源**（第一份是 `Cell.terrain`），
  两者可能失调（本项目刚在 §"单一事实来源"上吃过亏）。
- ❌ **`Drinking` 自己按半径扫格**：O(r²)。r=25 时 2601 格/次；1500 只猪 ≈ **390 万格/秒**，撑不住。

### 2.5 草补水 与 饮水 的关系 `[用户拍板：两者并存]`

> 用户原话：「**草也会补水 但渴的时候会去喝水**。」

**两套机制各司其职，互不取代。草的数值一行都不动。**

| 来源 | 触发条件 | 强度（每游戏分） | 在系统里的角色 |
|---|---|---|---|
| `Grazing`（**既有，不动**） | 站在**嫩草**上 且 `food < SATIETY_STOP(0.95)` 时，8 游戏分咬一口 | 每口 +2 → 可持续 **0.02** | **缓冲** —— 把口渴的下降速度削掉一截 |
| 🆕 `Drinking` | 渴（`ratio < 0.95`）且站在岸边 | **1.5**（连续） | **归零** —— 把口渴补回 0.95 |

**为什么不能只靠草**：口渴流失 **0.07/分**，草最多抵消 **0.02/分** → 净 **−0.05/分**。
⇒ 一只正常吃草的猪，口渴仍会在约 **1.4 游戏日**后见底。**草只能延后，不能阻止；湖才是解药。**

> 注意一个容易漏的细节：`Grazing` 在**不饿**时是**一点水都不给**的（`tick()` 开头 `if not wants_food(): return`）。
> 所以"吃得很饱 + 很渴"的猪**必须**去湖边 —— 这正是 `SATIETY_STOP` 与口渴机制咬合出来的行为，不需要额外写规则。

**为什么也不能只靠湖**：湖在半径 50 的环上、草原在环上另一侧，单程几十格。草的作用是把"去湖边"从
"每隔一会儿一次"降到"约一天一次"，猪的日常仍然是围着草地吃草 —— 这正是用户要的手感。

**两者叠加的净效果（设计期望）**：

```
口渴 100 ──(草 −0.02/分 缓冲)──► 约 1.0~1.4 天后跌到 0.2 危险档
          ──► drink 权重(×1.6) 压过夜间 rest ──► 出发，朝最近湖岸走
          ──► 到岸边站定，1.5/分 连续补 ──► 约 67 分回到 0.95 ──► 停
          ──► 走回草地继续吃草 …… 循环
```

即：**草把周期拉长，湖把周期归零。**

**`[不做]`** 不动 `GrassDef.water_per_bite`（用户没要求改）。若将来想让"草能基本养活"（即一直有草吃的猪几乎不用去湖边），
那是**草场平衡**的调整，属另一轮（同 §7-E）。

## 4. 关键逻辑设计

### 4.1 `Brain` 的新分支（与既有分支同构）

```
选中 "drink":
    if drinking.at_water():                 # 自己 4 邻格里有水
        last_drive = "drink"                # 站着不动 —— Drinking.tick() 自会补水
    else:
        var d := drinking.water_dir()        # 朝"最近的岸格"的单位方向
        if not _step_toward(mover, dirs, d):
            _wander_step(mover, dirs)        # 走不动 / 找不到 → 退化为游荡（下次再试）
        else:
            last_drive = "drink"
```

- 与既有 `feed` 分支**同一姿势**：已就位就站住，否则走一步；走不动就退化游荡。
- `_reset_timer()` 里给 `drink` 用"移动类"的时长（带抖动、受疲劳/年龄影响），
  **不要**给它 `rest` 那种长时长，否则一次决策会卡住很久。

### 4.2 "岸格"而不是"水格"—— 这是本设计最容易写错的地方

```
at_water()  = 自己 4 邻域（GridMover.DIRS）里存在 Terrain.WATER
water_dir() = 半径 WATER_SEARCH_RADIUS 内，找"最近的岸格"，
              岸格 := 某个水域格的 4 邻邻居中 Terrain.walkable 为真的那一格
              返回朝它的单位向量；找不到 → Vector2.ZERO
```

**为什么目标必须是岸格、不能是水格**：水不可踩，朝水格走最后一步必然被 `is_cell_free()` 拒绝 →
猪会在离水一格的地方反复"想进去又进不去"，表现为**卡在原地抖动**。
朝岸格走则目标本身可走，走近后 `at_water()` 自会变真、自动切到"站着喝"。

**岸格被别的猪占了怎么办**：不预先过滤"空不空"（占格是每帧变的动态事实），
走不过去就下一帧重算 —— 这与 `Brain` 现有"退化游荡、下次再试"的容错风格一致。

### 4.3 `Drinking.tick` 的独立性（重要）

`Drinking` 的补水**不依赖 `Brain` 是否选了 `drink`**：
只要"渴 + 在水边"就补。原因有两层：

1. **解耦**：让 `Drinking` 去读 `Brain.last_drive` 会把两个组件绑死（本项目明令禁止）。
2. **行为更对**：猪游荡时路过岸边，顺手喝两口是合理的；而 `Brain` 的 `drink` 驱动只管**导航**（往水边走）。

这与 `Grazing` 完全同构：`Grazing` 自己按计时器咬，`Brain` 的 `feed` 驱动只管把猪带到草上。

| # | 情况 | 处理 / 判断 |
|---|---|---|
| 1 | **水不可踩** | 目标必须是岸格，不是水格（§4.2）。这是本设计的第一原则 |
| 2 | **4 邻 vs 8 邻** | **已拍板：只认 4 邻**（与 `GridMover.DIRS` 一致）。若日后实测岸边抢位明显，再考虑放开 8 邻 |
| 3 | **只有一格岸的湖角** | 多只猪抢同一格 → 后来者挤在相邻格喝不到。MVP 先不管，观察后再定 |
| 4 | **渴死比饿死快**（0.07 > 0.05） | 渴永远是先到的死因。调参时 `DRINK_GAIN` 不能给弱 |
| 5 | **夜里睡着渴死** | **已拍板：要压过睡觉**。夜间 `rest ≈ 4.05` 是最强竞争者 → 靠 `THIRST_PANIC 0.2` + `DRINK_PANIC_BOOST 1.6`（≈6.4）压过去 |
| 6 | **幼崽更危险** | `Aging.speed_factor()` 让幼崽决策间隔 ×1.6（走得慢），而口渴流失速率一样；且 `cling`(3.0) 会把幼崽拉向妈妈 —— 妈妈在睡时幼崽可能渴死在旁边。MVP 不特殊处理；`THIRST_PANIC` 天然会让"极度口渴"压过 `cling`，算是自洽 |
| 7 | **⚠ 附带发现：开局没有可食草** | `GrassField.seed_existing()` 把 93 格草全播成 `max_bites`（满耐久），而 `Grazing` 只吃 `is_tender`（耐久 **< max**）→ **开局一格可食草都没有**，猪要等草扩散出新格才吃得上。这是**独立的既有问题**，不在本轮范围，但会**掩盖饮水效果的观察**（加完饮水后猪仍会先饿一阵） |
| 8 | **地形索引过期** | 索引靠 `terrain_changed` 重建。现在地形只在启动写一次 → 安全；将来若有"临时水位变化"，必须记得发该信号 |
| 9 | **目标方向全被占** | `free_directions()` 已排除被占格；`_step_toward` 失败 → 退化游荡，下一帧重试 |
| 10 | **岸格上有尸体** | `free_directions()` 默认不踩尸体，仅被围死才踩。岸格够多时无影响 |
| 11 | **岸格是高草** | 喝水的猪会"隐身"。这是既有隐蔽规则的正常结果，不特殊处理 |
| 12 | **全图都找不到水** | 本局不会（图 130、湖在半径 50 的环上，必在 80 内）。但为保险：找不到水时不产生驱动（猪照旧游荡，可能撞上），**不判死、不报错** |
| 13 | **可复现性** | `Drinking` 自身不用随机数（纯几何 + 需求读取）。但 `Brain` 的轮盘会消耗 `creature.rng` → **多一个驱动会改变随机序列**，同种子下的历史行为会变。这是**预期变化**（不是 bug），做存档/回放对比时要知道 |
| 14 | **驱动被摊薄** | 轮盘多一项会摊薄其它驱动的概率；且修好渴死之后猪活得更久，**种群动态（繁殖/家族）会跟着变**。需要专门复测"夜里是否还在睡、白天是否还在游荡" |
| 15 | 需求见底日志 | `Needs.restore` 在 value > 0 时会清 `_depleted_logged` → 喝到水后"再次见底"会重新报日志。正常行为 |

## 6. 验证方案（落地后必须做）

1. **加速探针（复用本轮手法）**：`speed=300` 跑到第 4 天，断言
   - `死因统计 == {}`（**没有渴死**）；
   - 存活猪的 `平均口渴 ≥ 0.6`（真的补上了）。
2. **几何断言**：取一只渴猪，断言它最终 `coord` 与某个水格 4 邻接；
   并断言它**从未**站到水格上（`Terrain.walkable(WATER) == false`，走上去 `move_to` 必然 `push_error`，日志里不许出现）。
3. **边界断言**：把猪直接生成在岸边 → 断言它**原地不动**就把口渴补满（走的是 `at_water()` 那条分支）。
4. **对比断言**：同种子跑"有饮水 / 无饮水"两版 → 有饮水版存活数显著更高、生存天数显著更长。
5. **回归**：`--import` 零脚本错误；`DefValidator` 仍报 **16** 个定义（不新增 `.tres`）；猪组件数 **11 → 12**。
6. **平衡观察**（人来判断，不看断言）：夜里是否出现"集体起床去喝水"？若是**每夜全军出动**，说明 `THIRST_PANIC` 门槛太高/`DRINK_RATE` 太慢，要调。
7. **临时探针用完即删**（项目纪律 §6.10）。

## 9. 落地记录 `[2026-09-20 已实现]`

**落地文件**：`creature/components/drinking.gd`（新）· `brain.gd`（第 8 个驱动 `drink`）·
`common/grid/grid_manager.gd`（派生地形索引）· `creature/pig/pig_def.tres`（挂载，猪 **11 → 12 组件**）·
`ui/creature_inspector.gd`（`DRIVE_LABEL` 加 `"drink": "饮水"`）。`--import` 零脚本错误。

**实现期的一处设计微调**：方案 §2.4 写的 `GridManager.nearest_cell_with_terrain(from, r, id)` **没有落地** ——
改成只暴露 `terrain_cells(id)`（原始格表），"最近岸格"的搜索放在 `Drinking._nearest_bank()` 里。
理由：①"岸格"只在饮水这个领域里有意义，不该进通用网格服务；②不留下没人用的 API（避免 `事实文档 §8.4` 休眠清单再涨一条）。
**"与半径无关"的性能特性不变**。

**实测调参**：`DRINK_GAIN` 初值 5.0 → **8.0**。
5.0 时权重被轮盘摊薄、"动身太晚"，远景猪（最近湖岸离草场约 **70+ 格**）赶不到湖边就渴死（实测 2/8）；
8.0 后加速跑到 1772 游戏分：**死因统计为空**、10 只**平均口渴 0.947 / 最低 0.910**。

**验证结果**（探针 7 项 + 加速跑 100×，全部 OK）：
A 地形索引 363 格 · B 岸上 `at_water=true` / 远点 `false` · B2 岸上 `water_dir=(0,0)`（不原地打转）·
B3 最近岸格可走且贴水、朝向点积 **1.000** · C 离开水边 `tick(60)` 仍 10.0 · D 岸边 `tick(10)`→**25.0**（正好 +15）、
`tick(60)`→**封顶 100** · D2 满后 `thirst_weight=0` · E 站在水格上的生物·帧数 = **0** ·
F 加速跑到 1772 游戏分（**> 渴死临界 1430**）**死因统计为空**。
（对照基线：做饮水**之前**同样加速跑 —— **7/7 全部死于「口渴 耗尽」**。）

**⚠ 新的瓶颈（不在本轮范围，但必须记下来）**：饮水修好后，死亡主因变成**饥饿** ——
加速跑到 2000 游戏分时 5 只猪**全部「饥饿 耗尽」且一口草都没吃到**。
疑似根因（读码可见的不一致）：`Brain` 的 feed 分支用 `GrassField.is_edible(coord)` 判"站住吃"，
而 `Grazing.tick` 只吃 `is_tender`（耐久 < `max_bites`）→ 猪站在**满耐久**格上会"站住但不啃"、永久卡死；
而草场播种时 93 格**全是满耐久**。**建议下一轮优先处理**（即方案 §7-E 那条）。
