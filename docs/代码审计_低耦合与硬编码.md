# 代码审计：低耦合 / 可复用性 / 逻辑严谨性 / 硬编码

**审计日期**：2026-09-21
**审计范围**：`creature/`（全部 15 个组件 + 基类 + 定义 + 2 个 `.tscn` + 全部 `.tres`）与
`world/`（地形 / 草原 / 湖泊 / 草场 / 渲染 / 相机）全部脚本与场景，另含直接消费它们的 `ui/` 与 `main.gd`。
**方法**：逐文件通读 + 全库 grep 交叉验证 + 两轮实测探针（性能与事件频率）。
**约束**：本次**只审计、不改功能**。所有结论都可复现，复现命令见文末。

---

## 〇、结论摘要

| 维度 | 评价 | 说明 |
|---|---|---|
| **低耦合** | **基本达标，两处破口** | 组件协议体系、`ShoreSampler` 协议、`EventBus` 总线这三处是教科书级的解耦。破口在 `main.gd`（上帝对象）与 `camera_rig.gd`（绕过 InputMap） |
| **可复用性** | **达标，一处名不副实** | "加物种 = 加 `.tres`" 真的成立（猪与主角共用全部组件，零子类）。但 `GrassField` 只有**一份** `GRASS_DEF`，"加一种草 = 配 `.tres`" 的注释**不成立** |
| **逻辑严谨性** | **良好，三处隐患** | 定义校验（`validate()` 四件套 + `DefValidator`）覆盖面很广。隐患：私有字段跨组件直写、`Brain` 驱动表的索引对齐、`Perception` 半径静默夹取 |
| **硬编码** | **良好，两类问题** | 数值绝大多数收在 `.tres` / 常量里。剩余问题：**同值复制**（`1440`、`"player"`、需求 id）与 **UI 里硬编码物种资产** |
| **性能** | **平均达标，有周期性尖峰与一个扩展天花板** | 平均 5.6 ms/帧（178 FPS）很好。但全图重绘造成 **~31 ms 尖峰**；`GrassField._on_tick` 是 **O(草格数)/tick 且无上限** |

## 一、P1 问题（建议处理）

### P1-1 `main.gd` 是上帝对象（403 行，6 类职责）

**位置**：`main.gd`

**现象**：文件自称"本文件是**组装根**……只负责接线"，但实际承担：

| 职责 | 落点 |
|---|---|
| 地形生成编排 | `_ready()` 前 60 行 |
| 湖泊锚点构造（把草原的圆区翻译成 `LakeGenerator.Anchor`） | `_ready()` |
| **家庭落位算法**（扇区均分 + 环带 + 朝水偏向） | `_spawn_family()` 23 行 |
| **主角落位算法** | `_spawn_player()` 56 行 + `_player_spawn_cell()` |
| **遗传**（性格均值±抖动、寿命均值×方差） | `_spawn_offspring()` 34 行 |
| 空格查找工具 ×2 | `_free_adjacent()` / `_pick_free_near()` |
| 调试壳 | `spawn_pig_random()` / `clear_creatures()` / `concealed_count()` |

**为什么是问题**：
- **可复用性**：`_spawn_family` / `_spawn_offspring` 是"种群初始化与繁殖"的业务逻辑，但它长在场景根节点上。
  想让第二种动物也按家庭开局（狼群、鸟群），只能复制粘贴这段代码。
- **可测性**：这些方法依赖 `_creatures` 节点与 `PackedScene`，没法脱离场景单独跑。
- 文件里 `_spawn_offspring` 已经显式取了 4 种组件（`Lineage`/`Personality`/`Aging`），
  说明它其实是"一个负责**繁殖**的服务"，而不是"组装"。

**建议**：抽出 `world/population.gd`（或 `PopulationSpawner`，Autoload 或普通 Node）承接
"落位 / 开局家庭 / 繁殖 / 遗传"，`main.gd` 只留"生成地形 → 调 population → 接总线"。
`_free_adjacent` / `_pick_free_near` 可一并搬过去（它们是落位工具，不是场景根的职责）。

**注意**：搬动时**不要改任何数值与顺序** —— `_spawn_player` 的注释明确写了
"与猪的落位**共用同一颗 rng**……顺序即契约"，换文件时保持调用顺序不变。

### P1-2 `MapRenderer` 忽略 `grass_changed` 的坐标，整张全图重绘

**位置**：`world/map_renderer.gd:19-20`、`world/grass/grass_field.gd`

```gdscript
# map_renderer.gd —— 信号明明带了坐标，却被丢掉
EventBus.grass_changed.connect(func(_c: Vector2i) -> void: queue_redraw())
```

而 `_draw()` 每次遍历 **130×130 = 16900 格**逐格 `draw_texture_rect` / `draw_rect`。

**而信号自己的注释写的是**：
> `signal grass_changed(coord: Vector2i)  # 任意耐久变化（啃食/再生），MapRenderer / Minimap 重画该格`

**"重画该格"这个意图在代码里没有实现。**

**实测证据**（探针，种子 20260918）：

| 项 | 数值 |
|---|---|
| `grass_changed` 发射频率 | **512 次 / 游戏日 = 0.36 次/真实秒** |
| 一次全图扫描的纯 CPU | **24.5 ~ 26.2 ms**（不含 `draw_*`，是**下界**） |
| A/B 对照（正常 vs 藏掉 MapRenderer） | 平均帧时间 **都是 5.6 ms**（178 FPS） |
| **最差帧** | 正常 **45.1 ms** vs 藏掉 **13.7 ms** |

**结论（要精确，别夸大成"持续掉帧"）**：
- **平均帧率不受影响** —— 0.36 次/秒 × 25 ms ≈ 0.9% 的 CPU，可以忽略；
- **但每约 2.8 秒会有一次 ~31 ms 的尖峰**（≈ 掉 2 帧）。这是**周期性卡顿**，不是持续低帧。
- ⚠ 我第一版探针把"每真实**分**"算成了"每真实**秒**"，得出"21 次/秒"，把严重程度夸大了 60 倍。
  **教训：报数字前先核对单位换算**（1440 游戏分 = 24 真实**分**，不是 24 秒）。

**为什么是问题（除性能外）**：这是**意图与实现不一致** —— 信号契约说"局部重画"，
唯一的消费者却做全量重画。将来加第二种会变的地形（雪、脚印、水渍）时，
每个人都会照着这个错误范式抄一遍。

**建议**（按代价从低到高）：
1. **最省**：给重绘加节流（每 N 毫秒最多重画一次），把尖峰摊平成可控的平均值；
2. **对症**：把 `MapRenderer` 拆成"静态底层（地形贴图，只在 `terrain_changed` 烘一次）"
   + "动态上层（只有活草的格）"，后者用信号带坐标做**脏格集合**；
3. 若要真做局部重画：用 `RenderingServer` 或把地图切成固定大小的区块（chunk），按区块失效。

### P1-3 `GrassField._on_tick` 是 O(草格数)/tick，且**没有上限**

**位置**：`world/grass/grass_field.gd:38-50`

```gdscript
func _on_tick(dt: float) -> void:
	var to_add: Array[Vector2i] = []
	for coord in tiles.keys():      # ← 每 tick 分配一个 N 元素的 Array
		...
```

**实测证据**：

| 项 | 数值 |
|---|---|
| `_on_tick` 一次耗时 | **0.53 ~ 1.04 ms**（462 格草，两轮测量有 2× 方差） |
| 折算 | ≈ **1.1 ~ 2.2 µs / 格**，**线性** |
| 当前每秒成本 | 60 tick/s × 0.53 ms ≈ **32 ms/秒 = 3.2% 单核** |
| 外推：占满一帧（16.67 ms）时的草格数 | **约 7,400 ~ 14,500 格** |
| 理论天花板 | 全图 **16900 格** |

**为什么是问题**：
- `Terrain.DEFS` 里 **`unknown`（黑土）的 `plantable = true`** ⇒ 草**可以**扩散到全图
  （实测一游戏日 343 → 462 格，+35%）。
- 一旦接近 7k~14k 格，**单是草场推进就会吃掉一整帧**，游戏直接不可玩。
- 这个天花板**没有任何代码在拦**，也没有日志提示。

**附带问题**：`tiles.keys()` **每个 tick 都分配一个新 Array**（462 个 `Vector2i`）。
GDScript 里 `for k in dict:` 直接迭代键**不分配**，这里白白制造了每 tick 一次的 GC 压力。

**建议**：
1. **立即**：`for coord in tiles.keys():` → `for coord in tiles:`（零成本，去掉每 tick 分配）；
2. **对症**：草场模拟**不必每帧跑**。它是慢过程（再生 60 游戏分/点），
   改成每 0.5~1 游戏分累积一次 dt 再推进，成本直接降 30~60 倍；
3. **根治**：只推进"附近有生物"的草格（空间分区），或给草的总量设上限（护草/退化机制）。

### P1-4 `GrassField` 只有一份 `GRASS_DEF`，"加一种草 = 配 `.tres`" 名不副实

**位置**：`world/grass/grass_field.gd:16` vs `world/grass/grass_def.gd:2-5`

`grass_def.gd` 的注释声称：
> 加一种草 = 配一份 `.tres`，不改逻辑。

但 `GrassField` 里：
```gdscript
const GRASS_DEF: GrassDef = preload("res://world/grass/grass_common.tres")
...
_establish(Vector2i(x, y), GRASS_DEF.max_bites)   # seed_existing
_establish(c, GRASS_DEF.seed_bites)               # _collect_spread
tiles[coord] = GrassTile.new(GRASS_DEF, coord, dur)  # _establish
```

**运行时结构其实是支持的**：`GrassTile` 每个实例都带自己的 `def`，`_recover` 也全走 `t.def.*`。
**缺的只是"怎么创建第二种草"的入口** —— `_establish` 把 `GRASS_DEF` 写死了。

**为什么是问题**：这是**文档承诺与实现不符**。项目自己在 §6.10 写着"校验纪律是本项目最容易自欺的地方"，
而这条正是同一类自欺：注释说可扩展，实际要改代码。

**建议**（二选一，别都做）：
- **要么实现它**：让地形/区域决定用哪份 `GrassDef`（例如给 `Terrain.DEFS` 每项加一个可空的 `grass_def` 字段，
  `_establish` 按 `cell.terrain` 取）—— 这同时让"黑土长劣草、草原长好草"变得只改数据；
- **要么改注释**：老实写"当前只支持一种草；加第二种需要改 `GrassField` 的 `_establish`"。
  **成本更低，也更诚实。**

### P1-5 `camera_rig.gd` 硬编码按键，绕过项目自己的 InputMap

**位置**：`world/camera_rig.gd:94-101`

```gdscript
if Input.is_key_pressed(KEY_W) or Input.is_key_pressed(KEY_UP):
	dir.y -= 1.0
...
```

而 `project.godot` 里**已经**定义了 `move_up / move_down / move_left / move_right` 四个 action
（还特意用了 `physical_keycode` 以便与键盘布局无关）。`project.godot` 的注释甚至写着
"原先相机平移硬编码 KEY_W/A/S/D + 方向键（camera_rig.gd）" —— **说明当时就知道要改，但只改了玩家侧**。

**为什么是问题**：
- **低耦合**：同一份"哪个键往哪走"的事实**存在两处**（InputMap + 代码）。改键位时必然漏一处。
- **可复用性**：InputMap 的全部价值就是"可重绑定"。相机绕开它 = 重绑定对相机无效，
  而且**玩家用 InputMap 改键后，相机会和玩家抢不同的键**，行为变得难以预测。
- 现在没炸只是因为两边**恰好绑了同一批物理键**。

**建议**：改成 `Input.is_action_pressed("move_up")` 等四个 action。**零风险**（当前键位完全相同）。

### P1-6 私有字段 `_depleted_logged` 被**三个**组件跨组件直写

**位置**：`creature/need.gd:8`（所有者）、`needs.gd:29-30,77`、`sprint.gd:282-283`、`thermal.gd:136-137`

```gdscript
# sprint.gd / thermal.gd —— 都直接读写 Need 的私有字段
if n.is_depleted() and not n._depleted_logged:
	n._depleted_logged = true
```

**为什么是问题**：
- 项目的核心纪律是"组件只通过协议对话"。`Needs` 提供了 `restore()` 作为**唯一**恢复入口，
  却没有提供**扣减**入口 —— 于是 `Sprint` 和 `Thermal` 各自造了一个，还顺手碰了私有字段。
- **没有一处知道"一条需求可以被哪些途径扣掉"**。加第三种扣减（中毒、流血、暴晒）时，
  第四个组件会再抄一遍这段 3 行代码，且**很容易抄漏日志口径**（这正是当初踩过的坑：
  出现"疲劳见底有日志、跑空没日志"的不一致）。
- 改名字段（`_depleted_logged` → `_empty_logged`）会**静默**打断两个文件（GDScript 无真私有，不报错）。

**建议**：给 `Needs` 加唯一扣减入口，把日志口径收进去：
```gdscript
## 扣减某项需求；返回"是否刚刚见底"（日志在内部统一打，调用方不必知道去重字段）。
func drain(id: String, amount: float) -> bool:
```
然后 `Needs.tick()`、`Sprint._drain_stamina()`、`Thermal.tick()` 三处都改成调它。
`Need._depleted_logged` 退回为 `Needs` 的私有实现细节。

### P1-7 `Brain` 的驱动表靠**索引对齐**，加驱动要改 5 处

**位置**：`creature/components/brain.gd:265-270` 与 `match chosen` 分支

```gdscript
var drives: Array[String]  = ["wander", "social", ..., "huddle"]
var weights: Array[float]  = [wander_w, social_w, ..., huddle_w]
var chosen := _roulette(drives, weights)
match chosen:
	"flee": ...
	"huddle": ...
	_: _wander_step(...)
```

**为什么是问题**：加第 11 个驱动必须**同时**改 5 个地方（常量、权重计算、`drives`、`weights`、`match` 分支），
而且 `drives` 与 `weights` 是**位置对应**的 —— 顺序错一位**不会报错**，只会让 A 驱动的权重喂给 B 驱动。
这是典型的"静默失败"，与本项目 `DefValidator` 想消灭的那类错误同源。

**当前规模**：文件 465 行，10 个驱动全部内联在 `_decide_and_act()`（约 165 行）。

**建议**（不必一次做到底）：
1. **最低成本**：在 `_roulette` 前加一句断言 `assert(drives.size() == weights.size())`，
   并把 `drives` / `weights` 相邻书写 + 注释"两者顺序必须一一对应"。能挡住一半错法。
2. **对症**：把每个驱动收成一个字典项 `{id, weight, dir, act}`，`match` 变成遍历。
   这样加驱动只需加一项，且顺序无关。
3. 若维持现状，至少把 `_decide_and_act()` 按驱动拆成 `_w_candidates()` / `_act(chosen)` 两个函数。

### P1-8 `ui/player_panel.gd`（801 行）职责过载，且硬编码了人类头像

**位置**：`ui/player_panel.gd`

**现象 A（职责）**：单文件同时做：竖版头像框、人形部位剪影与逐部位上色、6 条需求条、
年龄/阶段/性别、家族信息、**"历史 vs 当前"伤情对比**、面板开合动画、屏幕内收合。
801 行里混了**布局、取数、绘制、动画、状态机**五件事。

**现象 B（硬编码，与自身纪律矛盾）**：
```gdscript
const PORTRAIT_TEX: Texture2D = preload("res://creature/player/art/person.png")
```
文件开头的纪律写着：
> 与检视面板同一套取数方式：**只读通用组件**……不认识"猪 / 主角"这类具体物种 —— 换成任何生物都能显示。

但**头像被写死成人**。若把这个面板开到猪身上，会显示一张人像 —— 纪律与实现不一致。
（`family_tree.gd` 修过同一个病：它曾硬编码 `PIG_TEX` 导致"主角在族谱里还是一头猪"，
现在已改为 `def.texture` 优先 + `PIG_TEX` 兜底。）

**建议**：
- 头像改为 `def.texture`（与 `family_tree` 同一套写法），**顺手把 `PIG_TEX` 那种"用某个物种的图当通用兜底"
  换成中性占位**（纯色块或专门画一张占位图）；
- 把"人形剪影 + 逐部位上色"抽成独立控件（如 `ui/body_silhouette.gd`），
  把"历史 vs 当前对比"抽成独立控件。面板只负责编排。

## 三、明确**不需要**动的部分（避免过度重构）

这几处看起来"像"问题，但都是**有意的正确设计**，改动只会破坏它们：

| 位置 | 为什么不该动 |
|---|---|
| `Creature` 基类不认识任何具体组件 | 这是全项目的**地基**。`_aggregate_scale` / `_aggregate_tint` / `is_dead_state` 全部只做协议聚合 —— 一旦为了便利加一个 `get_body()`，整个组合架构就开始漏 |
| `Terrain.DEFS` 写成代码里的常量表 | 注释已论证过：属性是**结构性**的（能不能踩 / 藏不藏人），不是"每个地形一堆可调数值"。4 种地形还不到拆 Resource 的时候 |
| `ui/creature_inspector.gd` 用 `get_component(Body)` 而不是给 `Creature` 加便利方法 | 文件里明确论证过。UI 是"消费者"，它可以认识具体组件；基类不行。**方向是对的** |
| `water_layer.gd` 只认 `ShoreSampler` | 教科书级解耦：不认生成器、不扫 `GridManager`、不问 `Terrain`。是本次审计里**最好的一份代码** |
| `grass_field.gd` 不认识生物 / UI | 职责边界干净，只暴露查询与 `bite()` |
| `player.tscn` 与 `pig.tscn` 都是 `Creature + Sprite2D` | 场景结构极简是对的 —— 能力全在组件里，场景只负责"有个精灵" |
| `Sprint` / `Thermal` 用**绝对速率**而不是"基线的倍数" | 已经踩过坑并复盘过（时间尺度差 28.8 倍）。**别合并回去** |
| `Thermal._cold_multiplier()` 恒返回 1.0 | 它是**有意留的接缝**（季节/下雨接入点），不是死代码。对照 `PlayerIntent.apply()` 的 v1 直通 |
| `NeedDef.depleted_is_lethal` 默认 false、`need_fatigue.tres` 不写这一行 | 疲劳非致命是设计 |

| 指标 | 改动前 | 改动后 |

**③ 画面（像素级比对）**
- **拆层那一步**：改动前后首帧 **983,040 像素 0 差异**。
- 全部改完之后：出现 0.70% 差异，追查到是**主角面板的开场滑入动画**（`Tween` 的 `TRANS_BACK` 回弹）——
