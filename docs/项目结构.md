# 项目结构（分层 · 依赖方向 · 放文件的规则）

> 本文是**结构性约定**，不是设计文档。设计看 `事实文档.md`，本文只回答三件事：
> **东西放哪、谁可以认识谁、新文件该放哪。**
> 最后更新：2026-09-22（本轮做了结构梳理 + 低风险纠偏，见 §7）

---

## 一、一句话

**这是一个「数据驱动的组件式模拟内核 + 一层薄薄的编排层 + 一层只读的表现层」。**
没有继承树（零子类），物种差异全靠「挂哪些组件 + 配什么数据」。

### 2.2 依赖规则（硬约束）

| 规则 | 说明 |
|---|---|
| **R1** | `creature/` **不许**认识 `ui/`。逻辑不认识界面 —— 删掉整个 `ui/` 模拟照样跑（§6.8）。 |
| **R2** | `ui/` **只读**逻辑：可以 `get_component(...)` 读、可以订阅 `EventBus`，**不许**改生物状态。 |
| **R3** | 跨模块通信走 `EventBus` 信号，**不许**互相 `get_node` 找对方。 |
| **R4** | `world/` 的渲染节点（`map_renderer` / `grass_layer` / `water_layer` / `camera_rig`）**只读**，不写任何模拟状态。 |
| **R5** | `common/` 的**目标**是「不认识任何领域」。目前还剩 4 个类没做到（见 §2.3），**但只能减不能增**。 |
| **R6** | 组件之间靠 `requires()` 显式声明依赖，**不许**到处 `get_node` / `get_parent`。 |

**现状体检**：全项目 `get_node()` **0 处**，`get_parent()` **3 处**
（`sprint_arc.gd` 取宿主、`creature_inspector.gd` 往父节点挂族谱、`sleep_director.gd` 兜底取 Main）。
这三处都是「子节点/兄弟节点」的正常用法，不是耦合债。

### 2.3 仅剩的 4 处「固有」反向依赖（记录在案，不许再增）

| 位置 | 认识谁 | 为什么是固有的 |
|---|---|---|
| `common/family_registry.gd` | `Creature` `CreatureDef` `Lineage` | 它的**职责就是**「全局 `id → 活体 Creature` 注册表 + 种群计数」。不注册生物它就没有存在意义。 |
| `common/grid/grid_manager.gd` | `Terrain` | **一行**：`Terrain.walkable(cell.terrain)`。网格要回答「这格能不能踩」，而「哪种地形能踩」是 `Terrain` 的知识。 |

> **判据**：如果去掉这个引用，这个文件就没有职责了 → 固有。
> 如果只是「顺手用了下别的东西」→ 是债，要还。

## 三、目录职责表

| 目录 | 放什么 | **不放什么** |
|---|---|---|
| **`main.gd` / `main.tscn`** | 编排：世界生成、生成生物、执行繁殖请求、清屏、谁在扮演玩家 | 具体模拟规则（那属于组件/Def） |
| **`common/`** | **跨领域的全局服务（Autoload）** + 共享常量 + 值类型 | 领域逻辑、表现层 |
| **`creature/`** | 模拟内核：`Creature` 基类 + 定义资源类 + 组件 | 界面、渲染 |
| **`creature/components/`** | **跨物种可复用**的组件 | 只有一个物种需要的东西 |
| **`creature/<物种>/`** | 该物种专属：`*_def.tres` / `.tscn` / `data/` / 专属脚本 | 可复用的组件 |
| **`world/`** | 世界：地形、生成器、草场、湖、渲染层、编排层 | 生物内部逻辑 |
| **`world/<feature>/`** | 该 feature 的 Def + 生成器 + 数据（`grass/` `grassland/` `lake/`） | 别的 feature 的东西 |
| **`ui/`** | CanvasLayer 下的表现层：覆盖层、面板、HUD、可复用控件、主题 | 任何模拟状态 |
| **`assets/`** | 字体、图片等原始素材（按用途分子目录） | 脚本、场景 |
| **`docs/`** | 设计与结构文档 | — |

### 3.1 两条容易搞混的约定

**① `common/` 不是「底层库」，是「全局服务目录」。**
判断标准不是「它简不简单」，而是「**它需不需要是全局单例**」。
`GridManager` / `TimeSystem` / `EventBus` / `Log` 都需要 → 放这儿。
`Grid`（一个纯值类型）放这儿是因为它和 `GridManager` 是一对，不是因为它简单。

**② 领域专属的 Autoload 跟着领域走，不强制塞进 `common/`。**
`GrassField`（草场模拟服务）是 Autoload，但它住在 **`world/grass/`** —— 因为它是**草场领域的一部分**
（和 `grass_def.gd` / `grass_tile.gd` / `grass_common.tres` 是一伙的）。
**内聚 > 形式统一。** 8 个 Autoload 的分布因此是 7 个在 `common/`、1 个在 `world/grass/`，这是**故意的**。

## 四、新文件该放哪：判定四问

1. **它是「表现」还是「逻辑」？**
   表现 → `ui/`（界面）或 `world/`（世界渲染）。逻辑 → `creature/` 或 `world/`（生成器/数据）。
2. **它是「数值/清单」还是「有状态会做事的能力」？**
   数值/清单 → 一份 `.tres`（`*Def`）。能力 → 一个组件或一个节点脚本。
3. **它「只有一个物种需要」还是「任何物种都可能需要」？**
   一个物种 → `creature/<物种>/`。任何物种 → `creature/components/`。
   **目录位置即复用范围的声明。**
4. **它需不需要是全局单例？**
   需要 → 加进 `project.godot` 的 `[autoload]`，脚本放 `common/`（跨领域）或 `world/<feature>/`（领域专属）。

### 加一只新物种的标准流程（§6.9 的落地）

1. 建 `creature/<物种>/<物种>_def.tres`（`script = creature_def.gd`），填 `display_name` / `texture` /
   `component_scripts`（拖 `.gd` 脚本本体）/ `body_parts` / `active_needs`。
2. 建 `creature/<物种>/<物种>.tscn`：根 `Node2D` + `creature.gd`，`def = <物种>_def.tres`。
3. 需要新部位/需求 → 建 `creature/<物种>/data/*.tres`。
4. **不改任何系统代码。** 做不到第 4 条 = 架构有问题，先改架构。

## 五、目录契约：`DefValidator.SCAN_ROOTS`

`common/def_validator.gd` 的 `SCAN_ROOTS` 是**「定义资源住在哪」的唯一事实来源**：

```gdscript
const SCAN_ROOTS: Array[String] = ["res://creature", "res://world/grass", "res://world/grassland", "res://world/lake"]
```

⚠ **改目录布局时必须同步改这里。** 它是本文件仅剩的一处对外知识，
指的是**数据位置**（不是代码类型 —— 那条已经在 2026-09-22 用鸭子类型消掉了，见 §7）。

它同时是一条**纪律的自动检查**：这几个目录下的 `.tres` 约定**全部**是定义资源（都自带 `validate()`）。
出现一个没有 `validate()` 的，启动期会报出来 —— 要么是放错了目录，要么是新 Def 忘了写。

## 七、2026-09-22 本轮做了什么

### 7.1 修掉 3 处「目录与职责不符」

| 改动 | 理由 |
|---|---|
| `creature/sprint_arc.gd` → **`creature/player/sprint_arc.gd`** | 它**只被 `creature/player/player.tscn` 引用**（体力圈是主角专属表现），却放在 `creature/` 根。违反本项目自己写的规则「目录位置即复用范围的声明」（§4 判定三）。 |
| `def_validator.gd` 的**校验规则搬进各 Def 自己身上** | 见 §7.2 |
| 孤儿文件 | 只标记，不删（§6）|

### 7.2 ★ `common/` 的反向依赖：从 11 个类降到 4 个

**改之前**：`def_validator.gd` 里是一串 `if res is CreatureDef: ... elif res is BodyPartDef: ...`，
**点名了 8 个类**。这造成两个问题：

1. **反向依赖** —— 它住在 `common/`（底层），却认识 `creature/` 与 `world/`（上层）。
   于是 `common/` 永远不能当「可复用的底层」用。
2. **加一种 Def 就要回来改它** —— 「加物种是只配数据」的纪律（§4）在这里破了个口。

**改之后**：改成**鸭子类型** —— 只问 `res.has_method("validate")`，调它，收结果。
校验规则归各 Def 自己（本轮把 `BodyPartDef` / `NeedDef` / `PersonalityDef` 三条规则从校验器里搬回它们身上；
其余 5 个 Def 本来就是自带 `validate()` 的）。

**实测对比**

| | `common` 认识的上层类 |
|---|---|
| 改前 | `BodyPartDef` `Creature` `CreatureDef` `LifeDef` `Lineage` `NeedDef` `PersonalityDef` `GrassDef` `GrasslandDef` `LakeDef` `Terrain` = **11 个** |
| 改后 | `Creature` `CreatureDef` `Lineage` `Terrain` = **4 个**（全是固有的，见 §2.3）|
| 消除 | **7 个**：`BodyPartDef` `LifeDef` `NeedDef` `PersonalityDef` `GrassDef` `GrasslandDef` `LakeDef` |

> ⚠ **搬文件不降低耦合，改代码才降低耦合。**
> 这处原本的方案是「把 `def_validator.gd` 从 `common/` 搬出去」—— 那只让**目录**变诚实，
> 依赖关系一点没变。真正有效的是让校验器**不再需要知道那些类型**，
> 于是它**可以**名正言顺地留在 `common/`（因为它现在真的不认识任何领域了）。

**顺手加固**：原实现里「扫到一个不是 Def 的资源」是**静默跳过**的。
现在会报出来 —— 符合 §6.10.2「『0 条问题』和『根本没查到东西』必须长得不一样」。

**验证**（§6.10.1 要求「校验器必须被证明过能抓到错」）：故意注入 3 个错各跑一遍，
三条全部被启动期校验抓到、且运行期第二层校验也拒绝生成，**报错文本与重构前逐字一致**：

```
[定义校验] res://creature/pig/data/part_head.tres：部位 head 的 max_hp 必须 > 0（当前 0.0）
[定义校验] res://creature/pig/data/need_food.tres：需求 food 的 max_value 必须 > 0（当前 0.0）
[定义校验] res://creature/pig/pig_temperament.tres：性格分布 spread 不能为负（当前 -1.00）
[定义校验] 扫描 24 个定义文件，其中 5 个有问题（共 6 条）
```

新增守卫也验过（往扫描目录放一个没有 `validate()` 的 `.tres`）：

```
[定义校验] res://creature/pig/data/_probe_not_a_def.tres：这个资源没有 validate() ——
          Resource 目录下的 .tres 约定都是定义资源（放错目录？或新 Def 忘了写 validate()？）
```

### 7.3 本轮**没做**的（明确排除，不是漏做）

| 项 | 为什么 |
|---|---|
| **把 `player_panel`(801 行) / `creature_inspector`(351 行) / `player_hud`(242 行) 三个「代码建 UI」改成 `.tscn`** | **这是收益最大的一项**（Godot 的场景组织优势目前基本没用上：布局在编辑器里看不见、不能可视化调），但它是**真重构**，和「搬文件夹」不是一回事。**建议单独立项、单独验证。** |
| `world/` 拆出 `world/view/`（渲染四件） | 只是让分层在目录上更显眼。代价是 21 处硬编码 `res://` + 23 个 `.tres` 的 `path=`。**收益不抵风险。** |
| `creature/` 拆出 `creature/defs/`（7 个定义类） | 同上，且 `DefValidator.SCAN_ROOTS` 也要跟着改。 |
| `ui/` 拆出 `ui/widgets/` | 只有 2 个文件（`pixel_bar.gd` / `game_theme.tres`），拆了反而更碎。 |
| 删孤儿文件 | 删素材/数据是不可逆的，**留给你定**（§6）。 |

## 八、一条给未来的提醒

**这个项目的结构问题不在「文件夹怎么摆」，而在「三个大 UI 文件用代码建节点树」。**
`player_panel.gd` 801 行里，有 23 处 `.new()` 和 29 处 `add_child` ——
那是**本该由 `.tscn` 表达的布局**被写成了代码。
它带来的不是耦合，是**改不动**：想挪一个标签的位置得读代码算坐标。

真要继续优化结构，下一步就该做这个，而不是继续挪文件夹。
